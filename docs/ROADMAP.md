# 产品需求与路线图

## 产品目标

为管理 70 多台异构服务器的运维人员提供一个可追溯的 SSH 访问视图：知道谁、从哪里、在什么时间访问了哪台机器；高风险行为及时通知，发生故障时能看出监控链路在哪一层中断。

当前基础预览版解决“平台能运行、身份能管理、机器能接入、事件协议可验证”。下一交付重点是**真实事件到通知的闭环**，而不是增加展示型大屏。

## 核心使用流程

1. 管理员选择数据库与部署方式，配置域名/HTTPS，创建 operator/viewer 账号。
2. 批量规划服务器分组，逐台生成独立命令；目标机器完成注册并出现真实主机信息。
3. 后续采集器识别 SSH 成功/失败事件，先持久化，再上报，断线后补传。
4. 平台保存事件，匹配规则，在同一事务写入告警与待投递任务。
5. Worker 异步投递、重试并显示结果；值班人员确认告警后保留审计轨迹。

## 已交付：0.2 基础预览

认证与基础 RBAC、服务器管理、安装命令、四系统 Agent 注册/心跳、事件协议与去重 API、审计、双数据库迁移、两套部署方式、CI/Release 构建。Windows/Linux 支持 amd64/arm64 构建；目标机服务生命周期仍需按验证清单验收。

## 下一阶段 P0：采集与可靠传输

- Ubuntu/Debian 优先读取 journal，文件日志作为明确配置的备选；Alpine 使用系统 SSH 认证日志；Windows 读取 OpenSSH 对应事件日志。
- 采集源必须明确且可观测，避免同一事件同时从 journal 和文件重复读取。解析器以各系统/版本真实脱敏样本建立测试，不假设所有发行版格式一致。
- 本地持久化队列保存事件 UUID 和游标；收到服务端确认后才删除。进程崩溃、文件轮转、日志游标失效和网络断开都有明确恢复行为。
- 队列容量、磁盘不足、最旧未发送事件、最后成功采集/发送时间纳入 Agent 健康。没有 SSH 活动不等于采集停滞，不能仅用“最近事件时间”判断。
- 显式区分认证成功与会话建立；首个版本先保证成功/失败认证，后续再扩展会话生命周期。

验收：每种系统至少一台测试机产生成功/失败登录；API 中字段可核对；断网/重启后补传不丢失已落盘事件；同一事件重复上报只入库一次；日志轮转不静默漏读；满盘策略必须可见。

## P0：第一条可用告警闭环

先交付“配置的高权限账号登录成功 → Telegram 通知”，Windows 管理账号单独配置，不把 Linux root 规则硬套到 Windows。之后增加失败次数阈值和 IP 白名单。

- 告警、投递任务和原始事件分开存储，通知服务故障不阻塞事件入库。
- 失败退避重试、最大尝试次数、失败原因和人工重试入口。
- 去重键与冷却窗口分开设计；规则变更、确认告警、修改渠道均有审计。
- 只允许声明式规则；Webhook 地址限制和请求防护单独验收，禁止任意脚本规则。
- 通知密码/Token 加密存储，前端只返回掩码；主密钥轮换与备份恢复有操作文档。

验收目标（尚未测量，不是 SLA）：正常网络下事件产生到通知到达 P95 ≤ 10 秒；通知接口故障期间事件仍正常入库，恢复后可追溯补发；重试不重复产生同一规则的告警记录。

## P1：管理与生产加固

- 管理密码修改/重置、用户禁用、角色变更、MFA；失败登录审计。
- Agent 离线与采集故障分别告警，凭证轮换不依赖完整重装。
- Telegram 完善后增加 Webhook、SMTP，提供渠道测试和投递历史。
- 批量安装命令、Ansible 示例、可控升级与版本统计。
- 自动留存清理、备份恢复演练、数据库容量和查询性能监控。

## 上线顺序与退出条件

| 阶段 | 覆盖 | 退出条件 |
|---|---|---|
| 实验室 | 2–3 台，覆盖不同日志来源 | 采集、断线补传、通知、凭证撤销通过 |
| 小批量 | 约 10 台 | 连续观察、无无法解释的数据缺口，通知噪声可接受 |
| 全量 | 70+ 台 | 吞吐与磁盘测量达标、故障演练和恢复流程完成 |

容量以实际事件率、断线时长、保留期和通知峰值测试后确定，不按服务器数量直接承诺性能。所有性能结果注明硬件、数据库、数据规模和测试方法。

## 当前不做

远程 Shell、集中保存 SSH 私钥/密码、自动封禁 IP、替换服务器认证配置、通用 SIEM、Kubernetes 集群部署和可执行脚本规则。优先保障采集可靠、通知可追溯、升级可恢复。
